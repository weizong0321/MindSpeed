# 实验二（Step 1）：纯度核验后的验证结果

**结论：方向确认有效，但还不干净 —— 有条件通过。**

---

## 1. 设置

| 项 | 内容 |
|---|---|
| 数据 | `sample4`：**人工核验为同一款商品**的 14 个子样式 / 175 张图 |
| 训练 / 验证 | 266 条 / 84 条；验证集是**同一款、没见过的图**（测泛化而非记忆） |
| 起点 | 原始 base 的 DCP（与 sample3 完全一致，保证可比） |
| 对照 | BASE（原始权重）、FT 2-epoch(532)、FT 1-epoch(266) |

与 sample3 的唯一实质差别：**子样式纯度**。
sample3 按聚类纯度选 → `shoes_sneaker_031` 一个子样式里塞了 8 款鞋；
sample4 用 `coherence_*.png` 逐行核验，剔除了 16 个混合子样式。

## 2. 判据结果

| 模型 | A 组间 | B 组内 | **B−A** | C 串味 | D 归属 |
|---|---|---|---|---|---|
| BASE | 0.147 | 0.172 | **+0.025** | 0 | 0.214 |
| FT 1-epoch | 0.246 | 0.252 | **+0.006** | 14 | 0.345 |
| **FT 2-epoch** | 0.350 | **0.573** | **+0.223** | 6 | **0.417** |

指标含义：
- **A 组间重合度**：同一问题下、不同子样式的输出有多像 → 越低越好（目标 < 0.30）
- **B 组内重合度**：同一子样式、不同图片的输出有多像 → 越高越好（同款应当一致）
- **B−A 才是核心**：好模型应"同款一致、不同款可区分"
- **C 串味**：背包答案出现"表盘"、鞋答案出现"背"等跨品类词汇 → 目标 0
- **D 归属准确率**：输出最像哪个子样式的参考答案 → 随机约 0.07（14 类）

## 3. 结论

### ✅ 纯度修复是有效的：B−A 从 ~0 提升到 +0.223

- BASE：B−A = +0.025 → **完全没有区分能力**（输出又长又发散，什么都不像）
- FT 1-epoch：B−A = +0.006 → 同样没有区分能力，而且输出语无伦次
- **FT 2-epoch：B−A = +0.223** → **同款一致（0.573）、不同款可区分（0.350），
  这正是"认货"所要求的特征**

归属准确率也从 BASE 的 0.214 提升到 0.417（随机的 6 倍）。

### ⚠️ 但还不够干净

- A = 0.350 仍高于目标 0.30
- **C = 6 条串味，而且类型严重**：运动鞋被描述成"树脂表壳、双显窗口"，
  背包被描述成"蓝色双显窗、树脂表带怕水怕汗"，鞋被描述成"带促销标的白底商品图"
- D = 0.417 → 约 58% 的输出被归到错误的子样式

### ❌ 被推翻的假设：不是"epoch 2 退化"

我原以为要只训 1 个 epoch（因为 2-epoch 末段 loss 升到 0.56、grad norm 70）。
**实测反了**：1-epoch 更差（C=14、D=0.345、输出已经不通顺）。
逐样本 loss 方差很大（epoch 末 loss 3.73、grad norm 319），说明**收敛发生得比预想晚**，
2 个 epoch 反而是必要的。

## 4. 下一步（Step 2）的依据现在很硬

已有证据链：
1. 子样式纯度决定了模型表现（手表 8/10 纯 → 描述准确；运动鞋 2/10 纯 → 全错）
2. 换成核验过的纯子样式后，**区分能力确实出现了**（B−A: +0.025 → +0.223）
3. 但 14 个子样式 / 266 条样本太少，模型学到了骨架与词汇，**没学到可靠的"图→模板"绑定**

**⇒ Step 2：把"核验过的纯子样式"数量从 14 扩到 50–100，跑 2 个 epoch。**

具体做法（已具备工具）：
- `cluster_within.py` 在 85,575 张图上产出 3,457 个子样式（已有）
- `make_coherence_sheet.py` 每张表放 10 个子样式 → 300 个子样式只需 **30 张表**，
  人工判定约 **15 分钟**
- 预计可留下 60–120 个纯子样式 → 每个写一段答案（我已能读表写作）
- 规模：约 1,000 张图 / 2,000 条训练样本，训练约 5 分钟，评测约 10 分钟

## 5. 复现与踩坑

```bash
# 训练（2 epoch）
CONFIG=examples/qwen3_5/qwen3_5_0.8B_sample4_config.yaml bash examples/qwen3_5/train_qwen35.sh
# 转换
mm-convert Qwen35Converter dcp_to_hf \
  --dcp_dir /workspace/user_data/output/qwen3_5_0.8B_sample4/iter_0000532 \
  --save_hf_dir /workspace/user_data/output/qwen3_5_0.8B_sample4_hf \
  --origin_hf_dir /workspace/user_data/output/qwen3_5_0.8B_hf
# 评测
python examples/qwen3_5/eval_step1.py --model <HF目录> --tag <tag> --out <json>
```

踩坑：
- **`pkill -f` 会杀掉承载脚本自身**（脚本内容就在 bash 命令行里）。
  实测把评测进程和它自己一起杀了，返回 `EXIT -1`。要么按 PID 杀，要么用
  `$(printf ...)` 运行时拼 pattern。
- 服务器到 github 的 `git pull` 也不稳定（超时 129 s）。小文件改用 heredoc 直投更可靠。
- 评测日志被权重加载进度条刷屏，必须 `tr '\r' '\n' | grep -av "Loading weights"` 才看得清。
- 每条生成约 1.2 s（84 条 ≈ 9 分钟），必须后台跑，否则超过工具调用 10 分钟上限。
